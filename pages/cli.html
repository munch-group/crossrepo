Command line

Every command, as crossrepo --help reports it. The python API mirrors it, one call per command, and is documented in the API reference.

A --config PATH given before a command names the configuration file to use instead of the one that would be found; --refresh before or after one rescans the repositories rather than reading the stored catalog.

NoteWhere settings come from

A crossrepo.toml in the working directory is read instead of ~/.config/crossrepo/config.toml, not on top of it, and only the working directory itself is looked in. crossrepo config says which of the two is in force.

crossrepo cache

crossrepo cache [OPTIONS]

Show what the local cache holds, and check that it is sound.

Verification re-hashes every object and compares the digest with the key it is stored under, so it says whether the cache still holds what it claims. --repair removes the objects that fail, together with the readable links that stand for them; their content is fetched again the next time it is asked for.

Option
--verify re-hash every cached object and report any that do not match its key
--repair remove the objects that fail verification; implies –verify

crossrepo config

crossrepo config [OPTIONS] COMMAND [ARGS]...

Show the settings in force, or work on one of the two config files.

Called on its own it shows what is in force and which file that came from: the crossrepo.toml in this directory when there is one, else the config that applies everywhere. config local and config global name one of the two outright, and write the file if it is not there yet.

A --config PATH given before the subcommand names the file to show, instead of the one that would be found.

Subcommand
crossrepo config global Write or change the config file that applies everywhere.
crossrepo config local Write or change the crossrepo.toml in this directory.

crossrepo get

crossrepo get [OPTIONS] SPEC

Fetch [owner/]repo:path[@version] into the cache and print its path.

The path is the only thing written to standard output, so the command composes in a shell pipeline. When no version is given, the one chosen is named on standard error; when one is given and the file has changed since, that is said there instead.

Takes SPEC.

Option
-o, --out PATH also write a copy here
-u, --url print the URL of the version instead of downloading it
--config PATH path to config.toml
--refresh rescan repos instead of using the cached catalog

crossrepo info

crossrepo info [OPTIONS] SPEC

Print everything the catalog holds about [owner/]repo:path[@version].

Addressed exactly as crossrepo get addresses it, so asking about a file and fetching it differ in the verb and nothing else. Nothing is downloaded. The same lines crossrepo.info prints in a notebook.

Takes SPEC.

Option
--config PATH path to config.toml
--refresh rescan repos instead of using the cached catalog

crossrepo list

crossrepo list [OPTIONS] [REPO]

List result files, optionally limited to one repo.

Four columns: which repository, which file, where reading it goes, and what it holds. They are what a file is chosen on, and they are the same four crossrepo.list shows in a notebook, so that a listing is one thing however it is read. Everything known about one file is crossrepo info.

Takes [REPO].

Option
-p, --pattern GLOB filter by filename glob, e.g. ’*.csv’
--json print machine readable output
--config PATH path to config.toml
--refresh rescan repos instead of using the cached catalog

crossrepo refresh

crossrepo refresh [OPTIONS]

Rescan the repos and store the catalog.

A progress bar is drawn, one step per repository, when standard error is a terminal. Any root, organisation or repository that could not be read is named on standard error afterwards; the catalog is still written from what could be, and the status stays zero, since a scan that reached most of its sources has done its job.

Option
--config PATH path to config.toml
--refresh rescan repos instead of using the cached catalog

crossrepo share

crossrepo share [OPTIONS] PATH DESCRIPTION

Publish PATH, saying in DESCRIPTION what it holds.

Publishing is naming a file in the crossrepo.yml, and this is that written for you: the file is checked, the manifest is updated, and a file published as a symbolic link is stamped as well. Committing the crossrepo.yml is what makes the new version.

PATH has to be tracked by git already, since committing a file is the act of offering it. A symbolic link is published instead of its content, so what it points at must not be tracked: a target git holds as well would be published twice, once as bytes and once as a stamp that could disagree.

Takes PATH and DESCRIPTION.

Option
--config PATH path to config.toml
--refresh rescan repos instead of using the cached catalog

crossrepo stamp

crossrepo stamp [OPTIONS] [PATH]

Record what the published symbolic links in a repository point at.

A result file too large to commit is published as a symbolic link to wherever the pipeline wrote it, together with a stamp in the crossrepo.yml saying which content the link stands for. Git versions the link and not the bytes, so it is the stamp that makes the version: this command writes it, and committing the manifest publishes the new version.

Only the two stamp lines of each entry are rewritten, so comments and formatting survive and a stamping run reads as itself in a diff. A file must already be named in the manifest to be stamped, naming it being how it is published in the first place.

Takes [PATH].

Option
--check say what is out of date and write nothing; for a hook or for CI
